# Solver bot: notes

A candidate bot that plays a strategy precomputed with counterfactual regret
minimisation (CFR) on an abstract version of Discard Hold'em.

## Files

| Path | What it is |
|---|---|
| `bot/bot.py` | The bot: protocol loop, maps the real hand onto the abstraction, samples from the table, match overlay, fallback. |
| `bot/abstraction.py` | Shared by bot and trainer: evaluator, preflop classes, street features, bet abstraction, betting DAG. |
| `bot/strategy.py` | Generated by `train.py export`. The checked-in copy is the trained table the entry uses (24,862 iterations, 611 M deals). |
| `train.py` | `deals`, `solve` and `export` sub-commands. |
| `test_solver.py` | About 1 s of self-checks (evaluator, classes, tree legality, trainer/bot feature agreement, raise mapping). |

Submission zip: `bot.py`, `abstraction.py`, `strategy.py` at the top level (1.2 MB of `strategy.py` with the trained table).

## Abstraction

**Cards** (bucket = what a player knows about its own cards):

| Street | Feature | Buckets |
|---|---|---|
| preflop | exact suit-isomorphic class of the 3 hole cards | 1755 |
| flop (before discard) | S = mean percentile of the best 2-card keep against all holdings over 48 fixed runouts; V = its spread | 64 S bins x 8 V bins = 512 |
| turn | mean and spread over river cards of hand strength against the opponent's plausible kept holdings | 32 x 6 = 192 |
| river | hand strength against those holdings | 192 |

- Discard is fixed: keep the pair with the highest S. The opponent's plausible holdings after its discard D are the pairs {x, y} for which keeping {x, y} beats keeping {x, D} or {y, D} by that same S (within 0.02).
- Flop runouts come from an RNG seeded by the flop cards, so trainer and bot compute the same S and V.
- Bucket edges are quantiles of the deal pool and ship inside `strategy.py`.

**Betting**: fold, check/call, pot-fraction raises, all-in. Max 4 bets per street and the min-raise rule match the real game.

| Raise depth | Preflop sizes (pot fractions) | Postflop sizes |
|---|---|---|
| first bet / open | 1.0, 2.0 | 0.33, 0.66, 1.0 |
| first raise | 0.75 | 0.75 |
| later | all-in only | all-in only |

All-in is always offered. A size above 60% of the all-in amount is dropped.

**Public-state DAG**: inside a street the full action sequence is kept. At a street start only (pot, who made the last raise on the previous street) is kept, so histories with the same pot merge into one node. This is imperfect recall of earlier streets. It keeps the tree to 6,476 public states (terminals included) with 3,392 decision nodes (preflop 20, flop 236, turn 980, river 2,156).

**Sizes**: 758,044 infosets (decision node x bucket); 2,102,211 table entries (infosets x actions); `strategy.py` stores one byte per entry, zlib + base85: 2.54 MB for a 300-iteration smoke table, 1.22 MB for the trained table.

## Training algorithm

Chance-sampled discounted CFR (alpha 1.5, beta 0, gamma 2). Each iteration, every worker draws `--batch` deals from the pool and runs one numpy pass over the whole DAG for all of them at once: a forward pass for reach probabilities, then a backward pass for values and regrets. Where histories merge, the merged node adds their reaches together. This gives the exact sum of regrets over the merged histories, because the subgame below a merged node is identical for all of them. Regrets live in shared memory; each worker writes its own delta buffers and the main process adds them up.

## Running on the server (Linux, 14 cores, Python 3.11, numpy 2.x)

Copy the `solver/` folder. From inside it:

```bash
# 0. self-checks (needs the repo's pokerbots/ package one level up for the evaluator test)
python test_solver.py

# 1. multiprocess smoke test first (never run locally): about 1 minute
python train.py deals --flops 280 --workers 14 --out smoke_pool.npz
python train.py solve --pool smoke_pool.npz --checkpoint smoke_ckpt.npz --workers 14 --iters 20 --print-every 5

# 2. deal pool: 150,000 flops x 4 turns x 32 deals = 19.2 M deals, about 480 MB
python train.py deals --flops 150000 --workers 14 --out pool.npz

# 3. solve: checkpoints every 15 min, resumes automatically if ckpt.npz exists
nohup python train.py solve --pool pool.npz --checkpoint ckpt.npz --workers 14 \
      --batch 2048 --hours 8 --every 900 > solve.log 2>&1 &

# 4. export into the bot (any time, from the latest checkpoint)
python train.py export --checkpoint ckpt.npz --out bot/strategy.py
```

**Expected times** (from laptop measurements; the server should be similar or faster):
- Deal pool: about 465 deals/s per core, so about 50 min on 14 cores.
- Solve: one pass costs about 0.3 s of fixed overhead plus about 0.4 ms per deal (0.44 s for 1,024 deals). With `--batch 2048` and 14 workers that is about 1.2 s per iteration, about 24k deals/s, and about 24k iterations and 700 M deals in 8 hours.
- Memory: the pool needs about 2 GB in the main process while it is bucketed. Each worker uses about 300 MB at batch 2048.

**Progress output**: iterations/s, deals/s, mean max-regret per decision node (raw DCFR regrets, so read only the trend). At each checkpoint it also prints the mean absolute change of the average strategy since the last checkpoint; training has converged when that number stops falling.

## Bot behaviour

- Each request replays the hand history through the DAG:
  - The opponent's raises map onto the two neighbouring abstract sizes by randomised pseudo-harmonic mapping, cached per hand so the mapping stays fixed.
  - A bet always maps to a raise, never to a check. A real all-in maps to all-in.
  - Our own raises are recorded with the abstract code we chose.
- Actions below 4% probability are dropped before sampling. The pot fraction is converted to chips on the real pot and clamped to `[min_raise, max_raise]`.
- **Off-tree** (for example, the abstraction is already all-in but the real game is not): fall back to playing strength against pot odds.
- **Match overlay**, taken from `pokerbots/bots/range_bot.py`:
  - check-fold every hand once the lead is larger than the blinds left (`locked_in`, the same test as `equity_bot`);
  - when a pot can carry either player past a lock line, decide call/fold by match-win chance (`match_decision`).
- **Time guard**: below 3 s of time bank, check or fold. Any exception gives check/fold or the first card as the discard; the bot never crashes on a bad message.

## What was smoke-tested (laptop, single process)

- `python test_solver.py`: all 6 checks pass. The pool features equal the bot's own feature functions to within 1e-5; the only difference is uint16 rounding.
- `train.py deals --flops 40 --flops-per-job 20`: 5,120 deals in 10 s.
- `train.py solve ... --iters 300 --batch 64`: 300 iterations in 45 s, then `export`.
- `docs/starter_kit/engine.py solver/bot/bot.py .../random_bot.py --stage 2 --hands 20`:
  - seeds 7, 8, 9, 21: 20/20 hands, 0 notices, empty stderr;
  - 20 hands against the frozen rival_a bot: 0 notices;
  - no off-tree states in any of these matches.
- Timing, measured with a wrapper around `act`/`discard`:
  - startup 0.33 s;
  - mean 2-8 ms per action, max about 40 ms (the flop-table hand);
  - estimated 15-30 s per 1000 hands, depending on how many hands reach the turn and river.

## Not tested / open risks

- **Multiprocessing path runs on the server only.** The committed table was trained there; the laptop runs only the single-process tests.
- **Strength unknown**: no full-length match against `range_bot` or the frozen rivals, because the table is untrained.
- **Merged-history imperfect recall**: the DAG forgets earlier-street sizes beyond the pot. CFR has no convergence guarantee under imperfect recall; in practice it usually works with abstractions like this one.
- **Fixed discard rule**: the opponent model assumes the opponent discards by the same S rule. Bots that discard differently make the turn and river features less accurate.
- **Time bank**: a worst case where every hand reaches the river costs about 50 ms per hand, or 50 s per 1000 hands. That is still inside 150 s.
